Chapter 1

Concepts every developer needs

What the words mean in the business, and what they mean in code.

LedgerAn account that holds a running balance: Cash, Sales, Output CGST, each customer, each supplier. Every posted document adds lines to ledgers through a voucher.
In code: Table ledger_account (group_id, nature, system_code, party_id). Posting rules find ledgers by system_code. Party ledgers are created by the accounting module when it hears PartyChanged. Balance = Σ debit − Σ credit, never stored as an editable number.
Ledger groupA folder of ledgers in a tree (Current Assets → Sundry Debtors). The group decides the nature: asset, liability, equity, income or expense.
In code: ledger_group tree; nature of a ledger must equal its group's (DB CHECK).
VoucherOne accounting entry with debit and credit lines that add up to the same total.
In code: voucher + voucher_entry; created by listeners on InvoicePosted, PurchasePosted, PaymentRecorded …; ACCOUNTING_UNBALANCED if Σ Dr ≠ Σ Cr.
Debit / creditTwo sides of every entry. Assets and expenses grow on the debit side; liabilities, income and capital on the credit side.
In code: Store amount + side (DR/CR); show balances as '1,23,456.70 Dr'.
MasterA reference record documents copy from: party, item, ledger, doctor.
In code: Masters are editable and audited; documents snapshot master values at post time so later edits never change old bills.
DocumentA business paper: purchase invoice, sales invoice, return, receipt, transfer.
In code: Status DRAFT → POSTED → (REVERSED). Only drafts change. Posted rows have no UPDATE grant.
PostingMaking a document final. Stock moves, money is recorded, registers are written, all at once.
In code: The 12-step pipeline in BACKEND_IMPLEMENTATION §3, one database transaction.
BatchOne production lot of an item with its own batch number, expiry and MRP.
In code: batch(item_id, batch_no, expiry, mrp, cost); stock is per batch per location.
Inventory movementOne +/− row for every stock change, pointing to its document.
In code: Stock = Σ movements; stock_balance is a cache reconciled nightly. Never UPDATE quantities.
SnapshotCopy of master values stored on the document (party name, GSTIN, item name, HSN, GST rate, MRP).
In code: party_snapshot jsonb and line columns; printing and GST use the snapshot.
Tenant / company / branchTenant = the customer business; company = a GSTIN; branch = a shop or warehouse.
In code: tenant_id on every row (RLS); branch_id on branch-owned rows; tenant comes from the token only.
PermissionA named right like sales.invoice.post.
In code: @RequiresPermission on endpoints; usePermission() hides UI; never check role names.
Idempotency keyA client-made id that makes a retry safe: the second call returns the first result.
In code: Header Idempotency-Key on money / stock POSTs; POS uses the bill's clientId (UUIDv7).
Money as stringsAmounts travel as "123.4500" strings, never floats.
In code: Java BigDecimal; TS decimal.js; formatMoney() only for display.
Effective dateSettings and tax rates have a start date; the document date picks the value.
In code: SettingsFacade.get(key, date); hsn_tax rows by valid_from.
Problem DetailsThe standard error body with a code and field errors.
In code: RFC 9457: {type,title,status,detail,code,errors[{field,code}],requestId}; UI maps code → friendly text.
Hash chainEach posted record stores a fingerprint of itself and the previous one, so tampering is detectable.
In code: ADR-0016; columns prev_hash, hash; nightly verifier.
EngineThe shared maths library: same results on the server and offline.
In code: @meno/billing-engine (TS, built, 72 vectors pass) and its Java twin (to build).
Chapter 2

How a request flows

One backend (Spring Boot modular monolith), one web app (static Next.js SPA) reused inside the Electron desktop app. Every write follows this path:

Nginx / WAF→RequestId→JWT auth→Tenant + RLS→Idempotency→@RequiresPermission→@Valid DTO→Controller→Service @Transactional→Domain rules→Engine→Repositories + facades→Events (outbox)→Audit→Response / Problem Details

Money and stock documents then go through the 12-step posting pipeline (snapshot → engine → number → stock → posted + hash → event → audit) in one transaction.

Frontend builds

  • Tabs: Books · Licences · Bank · Income tax · GST · Others; red dot on a tab with errors; save jumps to the first error.
  • GSTIN Fetch calls GET /gstin/{gstin} and fills name, address, state, PAN; state field locks to the GSTIN.
  • PIN and IFSC fields auto-fill read-only fields; never let the user type state for a billing address.
  • Zod schema from @meno/validation (partySchema); the server re-validates every rule.

Backend builds

  • Request record SupplierRequest with @Valid nested records; @Gstin, @Pan, @PinCode, @IndianPhone annotations.
  • Service PartyService.createSupplier: duplicate check, licence rules, encrypt account number, publish PartyChanged.
  • accounting listens to PartyChanged → creates the ledger under SUNDRY_CREDITORS (never by name).
  • Bank change on update → status PENDING_APPROVAL until a second user approves (ADM-19).
