## Built so far (P1, 26-11-2026)
- `app_user`, `user_role` (V202611261701); mobile unique (`ux_app_user_mobile`, V202611262700). `CredentialCheck` (api): finds the user by email or mobile (`AppUser.normalizeMobile`), password check + lockout (`meno.identity.max-failed-attempts`, `lock-duration`), same result for unknown email and wrong password.
- `BootstrapOwner`: first tenant + OWNER from `MENO_BOOTSTRAP_*` on an empty DB.
- Sign-up (AUT-04 step 1): `SignupFacade` (api) → `SignupService` creates tenant + OWNER (mobile E.164) + `consent` in one transaction; Idempotency-Key replay; options (states, start options, terms version, password minimum) from data / `meno.signup.*`. Password minimum 10 (SECURITY.md). Email link built: `EmailVerification` (api) sends after commit through `notification.api.EmailSender` (SMTP); `/auth/verify-email`, `/auth/verify-email/resend`, `/auth/verification`. `OwnerEmailVerifiedCheck` implements tenancy's `GoLiveCheck`. Mobile OTP: `MobileVerification` (api) → `MobileVerificationService`: 6 digits, 5 min, 3 tries then IDENTITY_VERIFICATION_LOCKED (423), resend after 30 s (`meno.identity.verification.sms-*`), newest code only, hash salted with the row id, `verification.attempts` (V202611271000); SMS sent after commit through `notification.api.SmsSender`. Not yet: a real SMS provider (INT-02).
- `PasswordAccounts` (api) for the reset flow: `findForReset(email)` (active users only), `changePassword(userId, raw)` (policy check, clears lockout).
- `permission` / `role_permission` seed (V202611262101) read by `security/PermissionChecker` (permissions, never role names).
- Team step (AUT-09, 27-11-2026): `role` table (V202611271200, roles as data, `invitable` flag) + `invitation` / `invitation_branch` (RLS). `InvitationService` + `TeamController` `/api/v1/team`: `GET options` (invitable roles, branches via `tenancy.api.BranchDirectory`, `smsAvailable`, link days), `GET invitations` (page envelope), `POST invitations` (201), `POST invitations/{id}/resend`, `POST invitations/{id}/revoke`. Permissions `identity.invitation.view|manage` (OWNER). Link `meno.identity.invitation.link-base` + token (hash stored), valid `meno.identity.invitation.ttl` (7 d ⚠ to confirm), resend cooldown 60 s; sent after commit by email, and SMS when a provider is configured (mobile-only invites need SMS → 503 NOTIFICATION_CHANNEL_DISABLED). The first invite marks the TEAM step done (`tenancy.api.OnboardingSteps`). Duplicate checks run under RLS (this tenant only) so an invite never reveals another business's users; global one-email-one-user is enforced on acceptance. Not yet: accepting (`/api/v1/invitations/{token}`, proposed in `contracts/openapi/proposed/auth.yaml`), `user_branch`, the new role codes in the `Role` enum, counter PIN (PLT-10, P5).
- User management (/admin/users, PLT-06, 27-11-2026): `user_branch` (RLS) + `role.all_branches` (V202611271500; OWNER only, ROLES_AND_DASHBOARDS.md branch scope). `AppUser.roles` are now role codes (strings, FK to `role`); `Role` enum keeps only OWNER for sign-up / bootstrap. `UserAdminService` + `UserAdminController` `/api/v1/admin/users`: `GET options` (all roles with `assignable` = invitable and `allBranches`; branches the caller may hand out), `GET` (page envelope, `q`, `status=ACTIVE|DISABLED|ALL`), `GET {id}`, `PUT {id}/access` (whole role + branch sets, `version` in the body), `POST {id}/deactivate|reactivate`. Permissions `identity.user.view` (OWNER, BRANCH_MANAGER) and `identity.user.manage` (OWNER). Branch-limited viewers see people sharing a branch plus every-branch people. Non-assignable roles (OWNER…) are never granted or removed here. Nobody deactivates themselves; a change that leaves no active holder of `identity.user.manage` → IDENTITY_LAST_ADMIN. Deactivated users can't sign in; refresh already refuses them, so open sessions end within the access-token lifetime (15 min); role changes apply on the next refresh. `GET /auth/me` now returns `permissions` (`PermissionChecker.currentPermissions()`). Not yet: audit rows (audit module not built), copying `invitation_branch` → `user_branch` on acceptance (/invite page).
- Roles per tenant (/admin/roles, PLT-07, 27-11-2026; V202611271600). Overlay model: `role.tenant_id` null = MENO default (shared), set = the tenant's own role; `role_permission.tenant_id` null = default list (module migrations keep inserting these), set = the tenant's own list, used when `role_override(tenant_id, role)` exists (custom roles always have one). So new default permissions reach every tenant that hasn't changed that role. `role.locked` (OWNER: every permission, can't be edited), `role.description`, `archived_at`, audit columns, `version`; `permission_module(code, label, sort_order)` groups permissions on screen (**each module adds its row with its first permission**). RLS on role / role_permission (defaults visible to all, writes only for the tenant) and role_override. `PermissionChecker` resolves per (tenant, role) with a 30 s cache, evicted on this instance after commit (`evictTenant`). `RoleAdminService` + `RoleAdminController` `/api/v1/admin/roles`: `GET`, `GET {code}`, `POST` (label, description, copyFrom), `PUT {code}` (rename, own roles only), `PUT {code}/permissions` (whole list + `permissionsVersion`), `POST {code}/reset` (default roles), `DELETE {code}` (archive own role; refused while active people hold it or open invitations carry it). `GET /api/v1/admin/permissions`: catalogue by module with the roles holding each. Permissions `identity.role.view|manage` (OWNER). Custom role codes are generated (`CUSTOM_` + 12 hex), always invitable, never every-branch. Every change re-checks that someone active can still manage users and roles (IDENTITY_LAST_ADMIN). Team step and /admin/users use `findVisible(tenantId)`.

## Module rules
1. Permission strings are `module.resource.action`; each module seeds its own via a migration.
2. A tenant must always keep at least one Company Admin.
3. Permission checks live in services, not only controllers.
